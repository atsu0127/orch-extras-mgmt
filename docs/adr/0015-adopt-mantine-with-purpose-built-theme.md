# Mantineを用途固有のテーマで使い、モダンな実用アプリとして整える

## Context and Problem Statement

Phase 3・4 は素のHTML要素と約460行の共通CSSで実装し、機能確認を優先した。機能追加後に閲覧画面と管理画面をブラッシュアップするにあたり、フォーム・ダイアログ・ナビゲーション・ライト／ダークテーマを一貫した部品で実装したい。

一方、コンポーネントライブラリやAI生成コードの既定値をそのまま使うと、紫・青のグラデーション、過剰な角丸カード、ピル型バッジ、汎用SaaSダッシュボードといった画一的な外観になりやすい。影響するのは `src/styles.css`、共通コンポーネント、全ルートの画面、および `package.json` である。

## Considered Options

- Mantineを導入し、オーケストラ向けに定義したテーマと「モダンな実用アプリ」のレイアウトを使う
- shadcn/ui と Tailwind CSS を導入し、コピーした部品を個別に調整する
- Chakra UI を導入し、スタイルpropsを使って画面を作る
- 現在の素のHTMLとCSSを拡張する

## Decision Outcome

採用: **Mantineを用途固有のテーマで使う**。既存の Vite・React 19 構成へ Provider とCSSを追加して段階移行でき、フォームやレスポンシブ部品が揃っているため、shadcn/ui の Tailwind導入とコピーした部品の保守より実装コストが低い。Chakra UI に対しても、今回必要なCRUD部品の網羅性と公式例の多さを優先した。

画面案は「モダンな実用アプリ」を採用する。演奏会情報と次の練習を上部に置き、地図・カレンダー・備考・資料・出欠・問い合わせへ短い導線を設ける。色は温かいアイボリー、墨色、深いボルドーを基本とする。

Mantineは動作とアクセシビリティを担う部品として使い、既定テーマを完成デザインとはみなさない。設計書7.2の制約をテーマと共通部品に反映し、グラデーション、ガラス表現、装飾的な影、同形カードの多用、不要なピル型やアニメーションを避ける。

### Consequences

- 良い: 閲覧画面と管理画面のフォーム、状態、テーマを一貫した部品で実装できる
- 良い: ライト／ダーク、レスポンシブ、アクセシビリティの基礎をライブラリに任せられる
- 良い: 汎用SaaS風ではなく、演奏会情報を確認する用途に沿った優先順位を持てる
- 悪い: Mantineと関連CSSがクライアントバンドルに追加される
- 悪い: 既存のCSSと画面を段階的に置き換える移行作業が必要になる
- 悪い: Mantineの更新時にテーマと共通部品の見た目を再確認する必要がある
