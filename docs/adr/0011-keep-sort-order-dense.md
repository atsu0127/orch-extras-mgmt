# `sort_order` は 0 からの連番で保ち、並べ替えは2行だけ書き換える

## Context and Problem Statement

`practice_media` と `pieces` は `sort_order` で並びを持つ（設計書6.1）。設計書は列の存在と索引までしか決めておらず、値の刻み方と並べ替えの書き込み方は実装で決める必要があった。無料プランではサブリクエストが1リクエスト50件までで、D1 のクエリも1件として数える（設計書5.3）。並べ替えのたびに全行を書き直すと、曲が増えるほど上限に近づく。

影響するのは `src/lib/ordering.ts` と、それを使う `src/practices/mutations.ts`・`src/pieces/mutations.ts` である。

## Considered Options

- 0 からの連番で持ち、上下の入れ替えでは該当2行だけを `UPDATE` する
- 10, 20, 30 のように間隔を空けて持ち、挿入時は中間値を割り当てる
- 小数や文字列の順序キー（fractional indexing）で、挿入・移動を常に1行の書き換えで済ませる
- 連番で持ち、並べ替えのたびに一覧全行を書き直す

## Decision Outcome

採用: **0 からの連番、入れ替えは2行だけ**。並べ替えの UI は上下ボタンだけなので（任意の位置への移動やドラッグは持たない）、1回の操作で変わるのは隣り合う2行に限られる。連番なら「配列の index がそのまま `sort_order`」となり、読み出しの `ORDER BY` も一覧の表示順もずれない。

間隔を空ける案と順序キーの案は、任意の位置への挿入を安く済ませるためのものである。今回は末尾追加と隣との入れ替えしかないので、得られるものが無いのに値の意味が読みづらくなる。

全行の書き直しは行数が少なければ動くが、書き込み件数が一覧の長さに比例する。曲が20曲あれば1操作で20クエリになり、5.3の上限に対して割に合わない。

並べ替えの計算は DB を触らない純関数 `reorderRows` に置き、`sort_order` が飛んでいたり重なっていたりしても連番に直して返す。手で SQL を流した後（設計書の初期投入スクリプトなど）でも、1回並べ替えれば整う。

### Consequences

- 良い: 並べ替えの書き込みは、行数にかかわらず読み1回＋書き2回で収まる
- 良い: 並びの計算に DB が要らないので、端の判定や重複の直りを単体テストで確かめられる
- 悪い: 任意の位置への移動（ドラッグ並べ替え）を入れるなら、書き込み件数が動かした距離に比例する。そのときは順序キーへの移行を検討する
- 悪い: 連番であることは DB では強制されない。書き込みを `src/practices/mutations.ts` と `src/pieces/mutations.ts` に限る前提に乗っている
