# 外部リンクは共通部品で視認性を揃え、管理の行操作はアイコン化して密度を下げる

## Context and Problem Statement

Phase 8 の受け入れで、閲覧画面の外部リンクがタップ対象だと分かりにくいこと、管理画面の資料など1行あたりの「編集・上下・削除」が密集していることが指摘された（設計書13章）。どちらも機能は満たしているためリリース後の短い UI 改善（T9-1 / T9-2）として扱う。見た目の揃え方と、操作の見せ方を決める必要がある。

## Considered Options

- 外部リンク: `ExternalLink` に常時下線・リンク色・外部アイコンを付け、曲一覧の行リンクにも同じアイコンを使う
- 外部リンク: 画面ごとに「開く」ラベルやボタン風を個別に足す
- 行アクション: ↑↓ を `aria-label` 付きアイコンボタンにし、編集・削除はテキストのまま横並びの共通部品にする
- 行アクション: 編集・削除を Menu に集約し、↑↓ だけ外出しする
- 行アクション: 現状のテキストボタン4つのまま余白だけ広げる

## Decision Outcome

採用: **外部リンクは `ExternalLink` で視認性を揃え、行アクションは並べ替えのアイコン化＋横並び共通部品**。

リンク表現を1か所に寄せると Maps・カレンダー・資料・録音などで見た目がぶれない。画面ごとの個別調整は漏れやすいので落とした。行アクションは Menu 集約だと編集・削除が1タップ増えるため、日常操作の多さからアイコン化とレイアウト整理を選んだ。余白だけではボタン自体の占有面積が減らない。

アイコンは Mantine 推奨の `@tabler/icons-react` を使う。インライン SVG の散在を避け、外部リンクと並べ替えで同じ系統の線幅に揃える。設計書7.2どおり、並べ替えはアイコンのみでも `aria-label` を必須にし、編集・削除はラベルを残す。

### Consequences

- 良い: 閲覧側の外部導線が一目でリンクだと分かる。管理の子行がスキャンしやすい
- 良い: アイコンの追加・差し替えがパッケージ経由で一貫する
- 悪い: クライアントバンドルにアイコンライブラリが乗る（tree-shake 前提でもゼロにはならない）
- 悪い: Menu 集約よりボタン数は残るので、さらに操作を減らす必要が出たら再検討する
