# 削除の確認はネイティブの `<dialog>` で行う

## Context and Problem Statement

管理画面の削除は取り消せない。演奏会を消せば配下の練習・録音リンク・曲まで落ちる（設計書6.4）。設計書7章は画面の内容までしか決めていないので、削除前に何をどう見せて確認するかは実装側で決める必要があった。影響するのは `src/components/confirm-button.tsx` と、それを使う管理画面5枚である。

## Considered Options

- ネイティブの `<dialog>` を出す部品を1つ作り、全画面で使い回す
- `window.confirm()` を呼ぶ
- 削除ボタンを2度押しさせる（1度目で「本当に消す？」に変わる）
- 対象の名前を入力させる

## Decision Outcome

採用: **ネイティブの `<dialog>` を使う共通部品**。`ConfirmButton` に消える対象の名前と、連鎖して消えるものの説明文を渡す形にした。

`window.confirm()` は実装が最も短いが、文言に何が消えるかを添えても書式を整えられず、ダーク／ライトの見え方も OS 任せになる。スマートフォンではブラウザ名を含む素の警告が出て、この画面の一部だとは見えない。

2度押しは押し間違いで消える距離が近すぎる。一覧に同じ形のボタンが並ぶ画面なので、押した行を勘違いしていても止められない。

名前の入力は、消す対象が1件の会場や1本のリンクという粒度に対して重い。管理者は1人で、誤操作の代償は再入力で済む範囲である。

`<dialog>` を選んだのは、フォーカスの閉じ込め・`Esc` で閉じる・背面のスクロール抑止をブラウザが受け持つためで、モーダルを自作するより落とし穴が少ない。

### Consequences

- 良い: 「付いている録音リンク3件も一緒に消えます」のように、連鎖して消えるものを対象ごとの文言で出せる
- 良い: 見た目も配色も画面の他の部分と揃う
- 悪い: 部品が1つ増える。確認が要る操作は必ずこれを通す約束を、人手で守る必要がある
