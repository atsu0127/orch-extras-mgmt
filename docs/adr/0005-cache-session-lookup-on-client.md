# ルートガード用のセッション照会はクライアントで1回だけ行う

## Context and Problem Statement

設計書8.4は認可を二層で守ると定めている。実体はサーバ関数の middleware で、ルートの `beforeLoad` は体験を整えるためのものである。

T2-6 で `beforeLoad` を書くにあたり、ログイン済みかどうかをクライアントがどう知るかを決める必要があった。SPA モードなので初回の HTML にセッション情報を埋め込めず、サーバ関数 `getCurrentSession` を呼ぶ以外に手段がない。

素直に書くと `_authed` 配下へ遷移するたびに1回呼ぶことになる。設計書5.3のとおり1リクエストあたりのサブリクエストは50件までで D1 クエリもそこに数えられるため、画面遷移のたびに1クエリを足す形は避けたい。

## Considered Options

- `beforeLoad` のたびに `getCurrentSession` を呼ぶ
- 結果をクライアントのモジュールスコープに1回だけ保持し、以降は使い回す
- ロールを別の Cookie に平文で持たせ、クライアントはそれを読む

## Decision Outcome

採用: **クライアントに1回だけ保持する**（`src/auth/session-cache.ts`）。進行中の Promise ごと保持するので、同時に走る `beforeLoad` があっても呼び出しは1回にまとまる。ログイン成功時とログアウト時に明示的に捨てる。

ログイン画面の `beforeLoad` だけは、キャッシュを捨ててから必ずサーバに確かめる。セッション期限切れで `_authed` から飛ばされてきたときに古い「ログイン済み」を信じると、ログイン画面とトップの間を往復し続けるためである。

平文 Cookie 案は落とした。ロールを画面表示に使うだけとはいえ、書き換えられる値を認可の判断材料に近い場所へ置くと、後から参照箇所が増えたときに危うい。`__Host-oem_session` 1本に絞っておく方が、何が信頼できる値なのかを迷わずに済む。

### Consequences

- 良い: 画面遷移で D1 クエリが増えない。ログイン直後のダッシュボード表示は照会1回で済む
- 悪い: タブを開いたままセッションが切れると、画面上は入れているように見える。ただし実体はサーバ関数の middleware なので、データは一切返らず `/login` へリダイレクトされる
- 悪い: 別タブでログアウトしても、こちらのタブのキャッシュは古いまま。上と同じ理由で情報は漏れない
