# 選択中の演奏会は URL のクエリを正とし、`beforeLoad` で書き戻す

## Context and Problem Statement

設計書7.1は「`?concert=<id>` を正とし、指定がなければ Cookie → 進行中の直近 → 最新作成の順で解決する」と定めている。しかし**解決した結果をどこに置くか**は決めていない。

T3-1 でこれを実装するにあたり、閲覧側の3画面（ダッシュボード・練習日程・曲）がどうやって「いまどの演奏会を見ているか」を知るかを決める必要があった。影響するのは `src/routes/_authed/route.tsx` と、その配下の各ルートの `loader` である。

TanStack Router の `loader` は `loaderDeps` が変わったときに再実行される。そして `loaderDeps` が受け取れるのは search と params だけで、ルートコンテキストは受け取れない。つまり解決結果をコンテキストに置くと、演奏会を切り替えたときに子の `loader` が再実行される保証が無い。

## Considered Options

- 解決結果を `_authed` のルートコンテキストに置き、子の `loader` はそこから読む
- 解決結果を URL のクエリに書き戻し（`beforeLoad` から `redirect`）、子は search から読む
- 各サーバ関数が Cookie を読んで自分で解決する

## Decision Outcome

採用: **URL のクエリに書き戻す**。`_authed` の `beforeLoad` が解決し、`search.concert` と食い違っていれば `replace: true` でリダイレクトする。以降、子ルートは `loaderDeps: ({ search }) => ({ concert: search.concert })` と書くだけでよく、解決の分岐を各画面へ持ち込まずに済む。

コンテキスト案は、上に書いたとおり再実行の条件と噛み合わない。`loader` が古い演奏会のデータを返したままになる状況を、テストで捕まえるのが難しい形で抱えることになる。

サーバ関数側で解決する案は、解決が必要な回数だけ演奏会一覧のクエリが増える。ヘッダのセレクタも同じ解決を必要とするので、1画面で二重に解くことになる。無料プランのサブリクエスト上限（設計書5.3）に対して、得るものが無い。

この決定の副産物として、Cookie `oem_concert` はクライアント側（`document.cookie`）で読み書きする。解決がクライアントの `beforeLoad` で走る以上、そこから読めなければならないためである。認証の Cookie と違い、これは表示上の好みでしかなく、書き換えられても見えるものは変わらない（見せる範囲はサーバ関数側の認可が決める）。

### Consequences

- 良い: 子ルートは search を見るだけで済み、演奏会の切り替えが `loader` の再実行に確実につながる
- 良い: 選択が URL に出るので、共有したリンクが相手の画面でも同じ演奏会を開く
- 悪い: クエリが無い状態で開くとリダイレクトが1回挟まる。`replace` なので戻るボタンは壊れないが、初回表示がわずかに遅れる
- 悪い: 演奏会と関係のない管理画面のパスにも `?concert=` が付く
- 悪い: 演奏会一覧をクライアントに保持する（`src/concerts/concert-cache.ts`）ため、管理画面で演奏会を作成・編集・削除したら `forgetConcerts()` を呼ぶ必要がある。呼び忘れるとセレクタが古いままになる
