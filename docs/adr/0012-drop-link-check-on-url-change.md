# ボウイングURLを差し替えたら、前のURLの検知結果を捨てる

## Context and Problem Statement

`link_checks` は対象（`target_type` と `target_id`）ごとに最新の判定を1行持ち、その行には判定した URL も入っている（設計書6.1・9.4）。設計書9.5は「対象レコードが存在しない `link_checks` は Cron で掃除する」までしか決めていない。曲が残ったまま `bowing_url` だけ差し替えたときにどうするかは決まっていなかった。

放っておくと、管理者がリンク切れを直した直後の管理トップに、前の URL に対する `broken` が要確認として出続ける。次のチェックは翌日9:00なので、直したのに直っていないように見える時間が最長で24時間続く。影響するのは `src/pieces/mutations.ts` の `updatePiece` である。

## Considered Options

- URL が変わった（空にした場合も含む）ら、その曲の `link_checks` を削除する
- 残したまま、表示側で `link_checks.url` と `pieces.bowing_url` が食い違う行を無視する
- 保存のたびにその URL をその場でチェックし直して結果を上書きする
- 何もしない（翌日のチェックで直るのを待つ）

## Decision Outcome

採用: **URL が変わったら削除する**。削除は保存と同じサーバ関数の中で1クエリ増えるだけで、`link_checks` に残るのは常に「いまの URL に対する判定」だけになる。読み出し側（管理トップ、曲一覧）は食い違いを気にせず行を素直に使える。

表示側で無視する案は、判定結果を読むすべての画面が同じ条件を持つことになり、片方に入れ忘れると古い警告が出る。ADR-0006 で「付け忘れに気づけない守りは選ばない」と決めたのと同じ理由で落とした。

保存時に即チェックする案は、外部への `fetch` を管理者の保存操作に入れることになる。相手が遅ければ保存が待たされ、CPU 時間とサブリクエストの上限（設計書5.3）も保存の経路に持ち込む。手動チェックは管理トップに別の導線として既にある。

何もしない案は、リンクを直すという作業のいちばん最後で「直ったように見えない」という体験を残す。この機能の目的（設計書9章）に照らして最も避けたい。

### Consequences

- 良い: リンクを直した直後に、要確認の表示から消える
- 良い: `link_checks` の行は必ず現在の URL のものになる。判定を読む側に条件が増えない
- 悪い: URL を元に戻した場合、前の判定も消えているので次のチェックまで判定なしになる。判定なしは要確認として出ないので、見た目の害は無い
- 悪い: 更新のクエリが1件増える（1リクエスト内で読み1回・書き2回に収まる）
