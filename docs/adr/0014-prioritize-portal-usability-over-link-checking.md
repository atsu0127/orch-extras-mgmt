# リンク切れ検知を見送り、ポータルの日常的な利便性を優先する

## Context and Problem Statement

Phase 5 はボウイングリンクを毎日検査し、異常時に Slack へ通知する計画だった。しかし想定規模はエキストラ5名前後、リンクは十数件であり、管理者が日常的に受ける効果に対して Cron・外部通信・誤検知対応・Slack設定の実装と運用が重い。

一方、エキストラから管理者への問い合わせ、演奏会の備考としおり、会場の地図、カレンダー登録には明確な利用場面がある。管理者にとっても練習の複製は繰り返し入力を直接減らせる。影響するのは設計書2・6・7・9〜13章と `docs/tasks.md` の Phase 5 以降である。

## Considered Options

- リンク切れ検知を今回は見送り、問い合わせ・演奏会情報・外部サービス導線・練習複製を優先する
- 当初の Phase 5 をそのまま実装してから利便性機能を追加する
- Cron と Slack を外し、管理画面からの手動リンクチェックだけ残す

## Decision Outcome

採用: **リンク切れ検知を今回は見送り、問い合わせ・演奏会情報・外部サービス導線・練習複製を優先する**。少人数・少数リンクの現状では、リンク切れを自動監視する頻度より、演奏会前や練習登録時に毎回使う機能の方が費用対効果が高い。

問い合わせは管理者メールを1件だけ保存し、`mailto:` で端末のメールアプリを開く。アプリからは送信せず、エキストラの個人情報や問い合わせ履歴を保存しない。管理者本人のメールアドレスは、本人の合意がある団体共通の問い合わせ先として「個人情報を保持しない」原則の例外にする。

手動チェックだけ残す案でも、Google Drive などの認証画面を正しく判定できない問題と誤検知対応は残るため採用しない。

既に適用済みの `link_checks` テーブルは削除しない。未使用テーブルを消すために破壊的なマイグレーションを加える利益が小さく、将来リンクチェックを再検討するときの入口にもなるためである。ADR-0012 の判断は機能を再開した場合にのみ適用される。

### Consequences

- 良い: エキストラは演奏会当日の情報、資料、問い合わせ先を1か所で確認できる
- 良い: 管理者は練習の繰り返し入力を減らせる
- 良い: Slack Webhook、外部リンク検査、Cron の運用が不要になる
- 悪い: リンク切れは利用者または管理者が実際に開くまで分からない
- 悪い: `link_checks` は当面使われないテーブルとして残る
- 悪い: 管理者メールアドレス1件だけは個人情報を保持しない原則の例外になる
