# パスワード変更には管理者の現在のパスワードを要求する

## Context and Problem Statement

`/admin/settings` は両ロールのパスワードを変更できる（設計書7章）。設計書8.3が決めているのは「変更したらそのロールの全セッションを失効させる」までで、変更の操作そのものに追加の確認を要るかは決まっていなかった。

考えるべきは、セッションが 30 日有効で（設計書8.3）、パスワードはロールごとに1本の共有物という点である。管理者がログインしたままの端末を置いたまま離れれば、その端末を触った人が両ロールのパスワードを書き換えられる。エキストラのパスワードを変えられると、当日の関係者全員が入れなくなる。影響するのは `src/routes/_authed/admin/settings.tsx` と `src/auth/credentials.ts` である。

## Considered Options

- 変更フォームに管理者の現在のパスワードを必須で入れさせる
- `requireAdmin` を通っていれば追加の確認なしで変更させる
- ネイティブの `<dialog>` による確認だけを挟む（ADR-0010 の削除と同じ扱い）
- 直近のログインからの経過時間が短いときだけ追加の確認を省く

## Decision Outcome

採用: **管理者の現在のパスワードを必須にする**。エキストラのパスワードを変えるときも確かめるのは管理者のパスワードで、変更できるのが管理者だけだからである。

`requireAdmin` だけで通す案は、セッションを持っていることの証明にしかならない。ここで守りたいのは「セッションを持っている端末」ではなく「パスワードを知っている本人」であり、それを確かめる手段はパスワードの再入力しかない。

確認ダイアログだけの案は、押し間違いは防げても他人による操作は防げない。削除と違ってパスワードの変更は元に戻せず（前のパスワードを覚えていても、それを知る全員が入れなくなる時間が生じる）、押し間違いより他人による操作の方が重い。

経過時間で省く案は、この規模に対して状態を増やしすぎる。管理画面を開く頻度が低いので、省ける場面もほとんど無い。

あわせて次の2点も決めた。

- **新しいパスワードは12文字以上**。ハッシュは反復のない HMAC なので（設計書8.2）、強度の多くを長さに頼っている
- **管理者のパスワードを変えたときは、操作している自分のセッションも落ちる**。設計書8.3の「そのロールの全セッションを失効させる」をそのまま適用し、例外を作らない。画面はフォームを畳んで「新しいパスワードでログインしてください」とログイン画面への導線を出す

自分のセッションだけ残す実装も考えたが、失効の対象に例外を作ると「どのセッションが操作者のものか」を判定する仕組みが要る。パスワードを変えた直後に一度ログインし直すのは、変更が効いていることの確認にもなる。

### Consequences

- 良い: ログインしたままの端末を他人が触っても、パスワードは書き換えられない
- 良い: 現在のパスワードを間違えたときは、その項目のエラーとして返る。何も変わっていないことが画面で分かる
- 悪い: 管理者は自分のパスワードを変えるたびに再ログインが必要になる
- 悪い: 現在のパスワードの照合でハッシュ計算が1回増える。反復のない HMAC なので CPU 10ms（設計書5.3）に対しては問題にならない
- 悪い: パスワードを忘れた場合の復旧経路は画面に無い。`pnpm db:seed` で再投入する運用のままである
