# フェーズタスクの実施

進め方・規約・環境上の注意は `AGENTS.md` に従う。ここではタスク実施に固有の点だけを書く。

## 対象タスクの決め方

タスク ID の指定（例: `T1-1`、`T1-1〜T1-3`）があればそれを対象にする。ただし依存が未完了なら着手せず、先にその旨を伝える。

指定が無ければ次の手順で推薦し、着手の確認を取る。

1. `docs/tasks.md` の「進捗」を読み、どこまで終わっているかを把握する
2. 各フェーズの表から未完了タスクを拾い、**依存**列のタスクがすべて完了しているものを候補にする
3. 候補を次の順に並べる
   - 「進め方」のフェーズ依存図で、より若いフェーズにあるもの
   - 同じフェーズ内は ID 順（表は着手順に並んでいる）
   - Phase 3・4・5 のように並行できる分岐では、他タスクの依存元になっている数が多いものを先に
4. 「あなた（管理者）にお願いする作業」（A-1〜A-6）が前提になっているものは、その依頼が必要なことを添える
5. 上位2〜3件を、**依存が解けている理由**・**それが何を解放するか**・サイズ付きで示す

依存列に書かれていない前提にも注意する。表は主な依存しか書いていないので、設計書を読んで足りないものが無いか確かめる。

## 着手前に確認すること

1. `docs/tasks.md` で対象タスクの**内容・完了条件・依存**を読む
2. `docs/design.md` の該当章を読む（データモデルは6章、認証は8章、問い合わせ・外部サービス導線は9章、CI/CD は12章）

## フェーズ全体を実装するとき

複数のTタスクをまとめて頼まれた場合は、次の進め方を優先する。

1. フェーズ全体の依存・設計上の未確定事項・実装順・検証方法を1回の提案にまとめ、着手の合意を取る
2. ユーザーが「最後まで進めて」と指示した後は、設計変更・破壊的操作・外部作業が必要にならない限り、タスクごとの承認や設計節ごとの再承認を挟まない
3. `docs/design.md` と `docs/tasks.md` で設計が足りる場合、別の仕様書・実装計画書や設計専用PRを追加しない。フェーズ実装は原則1ブランチ・1PRにまとめる
4. Subagentを使う場合、共有ワークスペースを変更する実装Agentは常時1件だけにする。戻り値を受け取ったら `git status` と `git log` を確認してから次を起動する
5. 小タスクごとの二重レビューは避ける。DB・認証・マイグレーションなど高リスクな変更だけ追加レビューし、フェーズ末に仕様レビューと品質レビューを1回ずつ行う
6. Subagentが同じ差分で全検査を通した場合は親Agentが重ねて実行せず、差分変更後またはフェーズ末に再検査する

Subagentが `aborted` になった場合、UI上の終了を確認できるまで同じタスクを再起動しない。ユーザーから停止要求を受けたら、新しい操作を始めず `AGENTS.md` の停止手順に従う。

## 完了の基準

`docs/tasks.md` の完了条件を満たしたことを、**実際に動かして確認する**。確認方法が設計書の記述と噛み合わない場合は、代替手段を提示して合意を取り、合意した内容で完了条件そのものを更新する。

## 完了後に更新するもの

- `docs/tasks.md` — 「進捗」を書き換える。フェーズが終わったら見出しに「（完了）」を付け、次に着手できるタスクを1行で書く。管理者にお願いする作業（A-x）が済んだならチェックを入れる
- `docs/adr/` と `docs/design.md` の14章 — 設計書に書かれていないことを決めたなら ADR を追加し、14章の索引に1行足す。設計書の記述自体を変えたならその章も直す
- `README.md` — 構成やコマンドが変わったとき
